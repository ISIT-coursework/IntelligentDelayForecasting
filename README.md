# IntelligentDelayForecasting
Курсовая работа.

## Диаграммы Structurizr

Исходник общей модели — `diagrams/workspace.dsl`.
Подключённые через `!include` DSL-файлы проверяются вместе с главным workspace.
Для просмотра локально используются существующие команды `make run` и `make stop`.

### Структура командной модели

```text
diagrams/
  workspace.dsl             # сборка общей модели и представлений
  shared/
    people.dsl             # общие пользовательские роли
    external-systems.dsl   # внешние системы
    relationships.dsl      # согласованные связи и протоколы
    styles.dsl             # единое оформление
  model/
    web.dsl                # участник 1: веб- и мобильный интерфейсы
    api.dsl                # участник 2: API и координация запросов
    predictor.dsl          # участник 3: расчёт прогнозов
    data.dsl               # участник 4: обработка и хранение данных
  views/
    context.dsl
    containers.dsl
    web.dsl
    api.dsl
    predictor.dsl
    data.dsl
```

Это демонстрационная модель, а не утверждённая архитектура приложения.
В ней три роли, три внешние системы, пять контейнеров и четыре компонентных
представления по зонам ответственности. Технологии выбраны для тестового примера.

Файлы `model/` содержат фрагменты одной модели, а `views/` определяют, какие
элементы показать на диаграммах. В `data.dsl` директива `!element api` добавляет
компоненты обработки данных внутрь существующего API. PostgreSQL описана
отдельным контейнером. Разделение между участниками не создаёт дополнительные
сервисы: два представления API показывают разные зоны ответственности.

Один из четырёх участников дополнительно выполняет роль тимлида и координирует
главный workspace, общие файлы и межмодульные связи. Глобальные идентификаторы
задаются в `model/` и `shared/people.dsl`, `shared/external-systems.dsl`;
их переименование нужно согласовывать с владельцами использующих их файлов.

Предыдущий однофайловый пример сохранён в `diagrams/structurizr-test/`.
Его можно проверить отдельно: `make diagrams-check WORKSPACE_DIR=diagrams/structurizr-test`.

## CI диаграмм

Workflow `.github/workflows/diagrams.yml` запускается при создании и обновлении
Pull Request в `main`, при push в `main` и вручную через `workflow_dispatch`.

Workflow разделён на четыре самостоятельных jobs, отображаемых отдельными
стадиями в GitHub Actions:

| Стадия | Зависимости (`needs`) | Назначение |
| --- | --- | --- |
| `tests` | — | Тесты валидатора: `make diagrams-test` |
| `validate` | — | Валидация DSL и экспорт JSON: `make diagrams-validate`, `make diagrams-export-json` |
| `check-model` | `tests`, `validate` | Проверка технологий, связей и обязательных представлений: `make diagrams-check-rules` |
| `documentation` | `check-model` | Экспорт HTML: `make diagrams-export-html`, сохранение итоговых артефактов |

`tests` и `validate` запускаются параллельно. Остальные стадии ожидают успешного
завершения своих зависимостей. При ошибке зависимые jobs не запускаются.

Каждая стадия выполняется на отдельном runner. `validate` сохраняет JSON-модель
в промежуточном артефакте `structurizr-model` на один день; `check-model` и
`documentation` скачивают её. HTML создаётся из этой же проверенной JSON-модели.
Для отдельного локального запуска `diagrams-check-rules` или
`diagrams-export-html` сначала нужен экспорт JSON.

Сборка проверяет синтаксис и ссылки DSL, экспортирует модель в JSON и проверяет:

- технологии контейнеров и компонентов;
- описания и протоколы связей;
- наличие представлений контекста системы и контейнеров.

После успешной проверки Structurizr создаёт HTML-документацию. JSON-модель и
документация сохраняются в артефакте `architecture-<commit SHA>` на 30 дней.
После скачивания и распаковки артефакта откройте `site/index.html`, сохранив
остальные файлы рядом с ним. Эти проверки не заменяют архитектурное review.

Для локального запуска нужны Docker, Make и Python 3.9 или новее:

```sh
make diagrams-check
make diagrams-render
make diagrams-test
```

`diagrams-check` последовательно выполняет валидацию DSL, экспорт JSON и проверку
правил модели. `diagrams-render` включает эти этапы и экспорт HTML; тесты валидатора
запускаются отдельно командой `diagrams-test`. Результаты находятся в
`build/diagrams/model/workspace.json` и `build/diagrams/site/` и исключены из Git.
Исходный `workspace.json` и служебные файлы `.structurizr/` не обновляются этими командами.

Версия образа для проверки и экспорта зафиксирована digest в `DIAGRAM_IMAGE`
в Makefile. Локально используются только уже установленные образы
(`DIAGRAM_PULL_POLICY=never`); CI получает отсутствующий образ
(`DIAGRAM_PULL_POLICY=missing`). Обработка модели в контейнере выполняется без сети,
а исходники подключены только для чтения. Файлы `!include` должны находиться
внутри выбранного `WORKSPACE_DIR`.

По умолчанию локальные команды и CI используют `WORKSPACE_DIR=diagrams`.
Для проверки другого самостоятельного workspace укажите его директорию:

```sh
make diagrams-render WORKSPACE_DIR=diagrams/structurizr-test
```

Для обязательной проверки перед слиянием настройте защиту `main` в GitHub:
добавьте status check `documentation` и требование review тимлида.
Если ранее был настроен check `diagrams`, замените его: этот job больше не существует.
